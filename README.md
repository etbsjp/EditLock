# EditLock

WordPress標準の「他のユーザーが編集中です」表示は、あくまで注意喚起であり、実際の保存の競合（2人がほぼ同時に保存し、片方の変更が失われる）は防げません。EditLockは、先に編集を始めたユーザーがロックを保持している間、他のユーザーの保存を実際にブロックする投稿単位の排他ロックを追加します。

## 必要環境

- WordPress 6.7 以上
- PHP 7.4 以上

## 仕組み

1. 投稿の編集画面を開くと、その投稿に対するロックの取得を試みます（先に開いた人が保持）。
2. 編集画面を開いている間は、WordPress標準のHeartbeat APIに乗せてロックの有効期限（TTL）を自動延長します。
3. 保存ボタン（クラシックエディタの「更新」/「公開」、Gutenbergの「下書き保存」/「更新」/「公開」）をクリックすると、ロックの保持状況を確認します。他のユーザーがロックを保持している場合は保存をブロックし、モーダルで通知します。
4. 保存に成功する、または編集画面を閉じてHeartbeatが止まりTTLが切れると、ロックは自動的に解放されます。
5. サーバー側でも、クラシックエディタの投稿保存（`pre_post_update`）とGutenbergのREST保存（`rest_pre_insert_{post_type}`）の両方に実効的なゲートを設けているため、JSが無効化されている場合や通信エラー時でも二重保存は防がれます。

対応する投稿タイプはデフォルトで全て（管理画面の設定で除外可能）です。マルチサイトには対応していません。

判定は保存/更新/公開ボタンをクリックした瞬間に行われます。編集画面を開いただけの状態では何も表示されません。

## 設定

管理画面の **設定 > EditLock** から以下を設定できます。

- ロックの有効期限（秒）
- 対象から除外する投稿タイプ
- ゴミ箱への移動もロック対象にするかどうか（デフォルトOFF。オンにするとロック中の投稿は保持者を問わずゴミ箱への移動をブロックします。完全削除（force delete）は対象外です）
- 現在ロック中の投稿の一覧と、管理者による強制解除

### 既知の制限

- ゴミ箱ガードをオンにした状態で、投稿一覧から複数選択して一括ゴミ箱移動を行うと、対象にロック中の投稿が含まれている場合、その時点で処理が中断され、後続の投稿が未処理のまま残ることがあります。
- カスタム投稿タイプに対するXML-RPC経由の削除（`wp.deletePost`等）は、WordPressコアの実装上ゴミ箱を経由せず直接完全削除されるため、ゴミ箱ガードの対象外です。
- ブロック編集画面（Gutenberg）内の「ゴミ箱へ移動」ボタンでブロックされた場合、サーバー側では正しく拒否されている（投稿は公開状態のまま）にもかかわらず、画面上には一瞬「ゴミ箱へ移動しました」という成功通知が表示されることがあります。投稿一覧を再読み込みすれば実際には移動していないことが確認できます。
