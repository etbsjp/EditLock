# ETBS Edit Conflict Guard

> このファイルは自社ブログ・GitHub 向けの日本語ドキュメントです。WordPress.org 配布用（英語）の説明文は [`readme.txt`](readme.txt) を参照してください。掲載内容は基本的に揃えていますが、記載言語と想定読者が異なるため役割を分けて両方を維持しています。

製品ページ: https://etbs.jp/product/etbs-edit-conflict-guard/

WordPress標準の「他のユーザーが編集中です」表示は、あくまで注意喚起であり、実際の保存の競合（2人がほぼ同時に保存し、片方の変更が失われる）は防げません。ETBS Edit Conflict Guard は、先に編集を始めたユーザーがロックを保持している間、他のユーザーの保存を実際にブロックする投稿単位の排他ロックを追加します。

## 必要環境

- PHP 7.4 以上

WordPress のバージョン下限は設けていません（本プラグインが使用する WordPress の機能は
いずれも古くから提供されているものです）。

## 仕組み

1. 投稿の編集画面を開くと、その投稿に対するロックの取得を試みます（先に開いた人が保持）。
2. 編集画面を開いている間は、WordPress標準のHeartbeat APIに乗せてロックの有効期限（TTL）を自動延長します。
3. 保存ボタン（クラシックエディタの「更新」/「公開」、Gutenbergの「下書き保存」/「更新」/「公開」）をクリックすると、ロックの保持状況を確認します。他のユーザー（同じアカウントの別の編集画面を含む）がロックを保持している場合は保存をブロックし、モーダルで通知します。
4. 編集画面を離れる、または編集画面を閉じてHeartbeatが止まりTTLが切れると、ロックは解放されます。クラシックエディタの保存は画面が再読み込みされるため解放しますが、ブロックエディタの保存は同じタブで編集が続くため解放しません。
5. 自動保存はロックを取りも解放もせず、ロックに止められることもありません。
6. サーバー側でも、クラシックエディタの投稿保存（`pre_post_update`）とGutenbergのREST保存（`rest_pre_insert_{post_type}`）の両方に実効的なゲートを設けているため、JSが無効化されている場合や通信エラー時でも二重保存は防がれます。

対応する投稿タイプは、管理画面を持つ投稿タイプすべて（添付ファイルを除く）がデフォルトです（管理画面の設定で除外可能）。マルチサイト対応状況は「既知の制限」を参照してください。

判定は保存/更新/公開ボタンをクリックした瞬間に行われます。編集画面を開いただけの状態では何も表示されませんが、同じアカウントが別の編集画面ですでにその投稿を開いている場合だけは、通知が出ます。

クラシックエディタでは、他のアカウントがこのプラグインのロックを持っている間、WordPress 標準の「編集中です」ダイアログから「引き継ぐ」ボタンを消します（引き継いでもこのプラグインのロックは移らず、引き継いだ人が保存できなくなるため）。代わりに、誰が投稿を保護しているかを1行で示します。

## 設定

管理画面の **設定 > Edit Conflict Guard** から以下を設定できます。

- ロックの有効期限（秒）
- 対象から除外する投稿タイプ
- ゴミ箱への移動もロック対象にするかどうか（デフォルトOFF。オンにするとロック中の投稿は保持者を問わずゴミ箱への移動をブロックします。完全削除（force delete）は対象外です）
- 現在ロック中の投稿の一覧と、管理者による強制解除

### 既知の制限

- ロックはセッション単位で管理しているため、ロック保持者と同じアカウントであっても、別タブ・別ウィンドウ・別の端末から同じ投稿を開いた場合は保存をブロックされます（仕様であり、不具合ではありません）。同じアカウントの別セッションだとは分かりますが、アカウントが一致しても同一人物の証明にはならない（アカウントを共用している場合がある）ため、他のユーザーと同じ扱いにしています。メッセージが「あなた」ではなく「同じアカウント」と書いているのはこのためです。
- 自動保存はブロックしません。他のユーザーの自動保存はWordPress本体が別のリビジョンに回して投稿そのものに触れさせませんが、同じアカウントが同じ下書きを2つのタブで開いている場合は、両方のタブの自動保存が交互に下書きを上書きしうります。2つ目のタブを開いたときに出る通知は、その画面で編集を続けないよう案内しています。
- ブロックエディタの「引き継ぐ」ボタンは、プラグインからは消せません。引き継いでも動くのはWordPress本体のロックだけでこのプラグインのロックは移らないため、相手が編集画面を閉じるか、管理者が強制解除するまで保存はブロックされたままです。
- `WP_ADMIN` が定義されない経路で実行される保存（WP-Cron・WP-CLI・XML-RPC、およびフロントのテンプレートから直接 `wp_update_post()` を呼ぶコード）はブロックしません。メッセージを表示できず、訪問者の画面が落ちてしまうためです。なお `admin-post.php` と `admin-ajax.php` は WordPress 本体が `WP_ADMIN` を定義するため、そこへ POST するフロント側のフォームは、送信者がログインしている場合に限り引き続きブロックされます。ログインしていない訪問者からの保存は、そこでも素通しになります。REST APIと管理画面（クイック編集・一括編集を含む）からの保存も、引き続き判定します。
- ゴミ箱ガードをオンにした状態で、投稿一覧から複数選択して一括ゴミ箱移動を行うと、対象にロック中の投稿が含まれている場合、その時点で処理が中断され、後続の投稿が未処理のまま残ることがあります。
- カスタム投稿タイプに対するXML-RPC経由の削除（`wp.deletePost`等）は、WordPressコアの実装上ゴミ箱を経由せず直接完全削除されるため、ゴミ箱ガードの対象外です。
- ブロック編集画面（Gutenberg）内の「ゴミ箱へ移動」ボタンでブロックされた場合、サーバー側では正しく拒否されている（投稿は公開状態のまま）にもかかわらず、画面上には一瞬「ゴミ箱へ移動しました」という成功通知が表示されることがあります。投稿一覧を再読み込みすれば実際には移動していないことが確認できます。
- マルチサイトには対応していません（ロックはサイトをまたいで共有・認識されません）。
